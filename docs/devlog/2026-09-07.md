# 開發日誌 2026-09-07

## Android — MP4 本地錄影方向修正

使用者回報「RTSP client 端看到的畫面和手機上不一樣」（照片實測：手機預覽直向已轉正，client 端橫向/轉了 90°）。

確認這不是新 bug，而是 [2026-09-04](2026-09-04.md) 就已經拆成三條獨立追蹤項的其中兩項：
`configurePreviewTransform`（[CameraStreamer.java](../../android/src/MediaStreamTest/src/veg/mediacapture/sdk/test/rtspserver/CameraStreamer.java)）只是 TextureView 的顯示層變換矩陣，只影響手機螢幕上的預覽，完全不碰真正送進 `H264Encoder` 的像素——所以 RTSP/MP4 拿到的畫面從頭到尾都是感光元件原始方向（`SENSOR_ORIENTATION=90`），跟手機上經過矩陣修正的預覽不一致。

### 已修：MP4 本地錄影（零風險）
`LocalRecorder.maybeStart()` 在 `muxer.start()` 前呼叫 `muxer.setOrientationHint(90)`——純容器層 metadata，不碰任何像素、不重新編碼，不影響 Camera2/encoder 核心 pipeline。實機驗證：錄一段、拉下來用 ffprobe 確認 `rotation` metadata 正確寫入，並用 ffmpeg 抽幀（自動套用 rotation tag）確認畫面確實轉正，跟手機預覽一致。

### 未修：RTSP 即時串流方向
裸 RTP/H.264 沒有容器層級的 rotation metadata 機制，這條路只有兩個選項：
1. 接受現況——client 端（ffplay/VLC/GCS）收到的就是感光元件原始方向，由 client 軟體自行處理旋轉。
2. 在 Camera2→encoder 之間插入 GL 旋轉層，真正把像素轉正——這個在 09-04 就已經因為風險考量被否決過，今天沒有改變這個決定，仍待使用者明確要求才會動工。

## iOS — Photos 儲存失敗（PHPhotosErrorDomain error -1）根因與修正

使用者按 Stop 後看到「Failed to save to Photos (PHPhotosErrorDomain error -1)」。追查發現：`project.yml` 是 XcodeGen 每次 `xcodegen generate` 重新產生 `Sources/Info.plist` 的來源檔，但 `NSPhotoLibraryAddUsageDescription`（以及 `UIFileSharingEnabled`/`LSSupportsOpeningDocumentsInPlace`）在 09-05 只被直接加進「產生出來的」`Info.plist`，沒有加進 `project.yml`——所以每次建置前的 regenerate 都會把這個權限字串洗掉，iOS 因此直接拒絕 Photos 權限請求。已修正到 `project.yml`（commit `6469869`，僅在 `claude/dazzling-varahamihira-07671b` 分支）。

**Codex 獨立交叉驗證**（只讀取+`/tmp` 暫存驗證，未改動程式碼）確認了這個判斷，並額外抓到一個更關鍵的協調問題：**`master` 分支跟 `claude/dazzling-varahamihira-07671b` 分支是兩份不同進度的程式碼**——`master` 的 `project.yml`/`Info.plist` 沒有這個修正（也沒有 `NSPhotoLibraryAddUsageDescription`），且 `master` 的 `ContentView.swift` UI 文字是「Save Recording Locally」+ GPS/Timestamp 選項（對應那份平行的 GPS/Overlay/SRT 實作），跟本分支的「Record to Local File」不同。使用者手機上測試看到的 UI 文字是「Record to Local File」，確認測的是本分支的 build，不是 `master`。

**教訓**：之後查任何 iOS 端的 bug，第一步務必先確認「實機上測的 app、Xcode 打開的 checkout、git 分支」三者一致，再往下推理，否則會在錯的程式碼版本上找原因。
